# NEXON Open API 데이터 처리 기준

> 마지막 확인: 2026-07-26
>
> 적용 범위: FC ONLINE Open API로 조회한 원본 응답, 정규화 결과, 경기 참조값, 파생 집계, 추천·실험 로그, 로컬 캡처와 백업
>
> 상태: 운영 전 필수 구현 기준. 최신 공식 약관이 이 문서보다 우선합니다.

## 1. 핵심 결론

[NEXON Open API 이용약관](https://openapi.nexon.com/support/) 8.6~8.7은 애플리케이션 개인정보처리방침 게시, 이용자의 열람·정정·철회 등 요청 대응, API로 가져온 모든 NEXON Game Data에 최대 30일 TTL 적용을 요구합니다. 9.1은 이용 중단이나 개인의 삭제 요청 시 관련 사본도 삭제하도록 요구합니다. 확인한 약관의 표시상 최종 갱신일은 2025-04-21입니다.

이 프로젝트는 약관이 파생 집계나 가명 처리 데이터에 TTL 예외를 준다고 가정하지 않습니다. 원본에서 만들어진 정규화 결과·집계·연구 로그에도 보수적으로 같은 만료 정책을 적용합니다. 공개 저장소에는 실제 응답을 변형한 fixture가 아니라 합성 fixture만 둡니다.

## 2. 데이터 분류와 저장 원칙

| 데이터 | 저장 위치 | 최대 보존 | 공개 저장소 |
| --- | --- | --- | --- |
| API 원본 응답 | 접근 제한된 임시 로컬 또는 운영 저장소 | 조회 후 30일 이내 | 금지 |
| OUID·실제 matchId·닉네임 | 접근 제한된 매핑 또는 임시 저장소 | 조회 후 30일 이내 | 금지 |
| 정규화 경기와 파생 집계 | 운영 분석 저장소 | 보수적으로 조회 후 30일 이내 | 금지 |
| 추천·실험 로그 중 API 파생 문맥과 결과 | 접근 제한된 연구 저장소 | 보수적으로 조회 후 30일 이내 | 금지 |
| 특정 이용자와 연결되지 않은 전술 설정·규칙 버전 등 코드 메타데이터 | 일반 프로젝트 저장소 | 프로젝트 정책 | 가능 |
| 사람이 만든 합성 fixture만 허용 | `src/lib/fconline/__fixtures__/success` | 제한 없음 | 가능 |

가명 ID는 익명 데이터가 아닙니다. 동일 사용자를 계속 연결하거나 제한된 매핑표로 원래 이용자를 찾을 수 있으므로 접근 통제와 삭제 대상에 포함합니다.

## 3. 모든 저장 레코드의 수명주기 필드

API 데이터 또는 그 파생값을 저장하는 레코드에는 다음 필드를 함께 둡니다.

```text
data_subject_pseudonymous_id
source_record_refs
pulled_at
expires_at
consent_status
deletion_status
```

- `expires_at`은 `pulled_at`에서 30일을 넘지 않게 계산합니다.
- `source_record_refs`는 공개 가능한 ID가 아니라 내부 가명 참조입니다. 실제 OUID와 matchId 매핑은 별도 접근 제한 영역에 두고 함께 만료시킵니다.
- `deletion_status`는 레코드가 존재하는 동안 `active` 또는 `pending_deletion`만 표현합니다. 삭제가 끝나면 연결 가능한 상태 레코드도 함께 제거하고, 필요하면 식별자 없는 삭제 작업 건수·완료 시각만 별도 운영 감사 로그에 남깁니다.
- 만료된 데이터는 표시·분석·학습에서 먼저 제외한 뒤 원본, 파생값, 캐시와 백업 사본까지 삭제합니다.
- 계속 필요한 데이터는 기존 사본의 만료를 연장하지 않고 API에서 다시 조회해 새 `pulled_at`과 `expires_at`을 부여합니다.
- 서로 다른 시점의 API 데이터를 결합한 파생값은 가장 이른 원천 데이터의 만료일을 넘기지 않습니다.

## 4. 캡처와 fixture

`npm run capture:fixture`가 만드는 `src/lib/fconline/__fixtures__/captured/<캡처시각>`은 실제 NEXON Game Data가 들어가는 로컬 임시 영역입니다.

- 현재 캡처 스크립트는 자동 삭제나 `expires_at` 관리를 구현하지 않았으므로 운영자가 캡처 시각을 기록하고 30일 이내 직접 삭제해야 합니다.
- `captured`는 Git에 추가하거나 다른 사람에게 배포하지 않습니다.
- 공개 테스트가 필요한 경우 필드 구조와 경계 사례를 사람이 다시 구성한 합성 데이터로 작성합니다.
- 실제 응답에서 닉네임과 OUID만 바꾼 자료는 합성 fixture로 간주하지 않습니다.
- 합성 fixture에는 `fixture-*`, `테스트구단주`처럼 실데이터가 아님을 알 수 있는 값을 사용하고 생성 근거를 코드 리뷰에서 확인합니다.

## 5. 이용자 요청과 동의 철회

외부 사용자가 이용하는 서비스로 배포하기 전에 다음 절차를 구현합니다.

1. 사용자가 열람·정정·삭제·동의 철회를 요청할 접점을 제공합니다.
2. 가명 ID와 제한된 매핑표로 대상 레코드와 사본을 찾습니다.
3. 원본 응답, 정규화 결과, 파생 집계, 추천 로그, 캐시, 내보내기와 백업에서 삭제합니다.
4. 삭제 후에는 NEXON Game Data나 다시 연결할 수 있는 식별자를 감사 기록에 남기지 않습니다. 법적으로 필요한 비식별 운영 집계가 있다면 별도 근거와 보존 기한을 정합니다.
5. NEXON이 삭제 또는 이용 중단을 요청하면 같은 절차를 즉시 수행합니다.

삭제 대상이 될 데이터를 Git 이력, 패키지, 논문 부록이나 물리적 산출물에 넣지 않습니다. 이런 위치는 요청에 따른 완전 삭제를 어렵게 만듭니다.

## 6. 개인정보처리방침과 고지

외부 사용자에게 앱을 제공하기 전, 화면에서 쉽게 찾을 수 있는 개인정보처리방침을 게시합니다. 최소한 다음 내용을 실제 구현과 일치하게 설명합니다.

- NEXON이 경기 데이터의 출처라는 사실과 NEXON의 보증·제휴로 오인하지 않게 하는 고지
- 수집하는 정보, 수집 목적, 처리 방식, 저장 위치와 보존 기간
- 제3자 제공 여부와 접근 권한
- 열람·정정·삭제·철회 방법
- 문의와 침해 대응 연락처
- 30일 TTL과 재조회 방식

정책 문구만 만들고 코드가 다르게 동작해서는 안 됩니다. 저장소, 캐시, 분석 로그와 백업의 실제 삭제 흐름을 배포 전에 시험합니다.

## 7. 보안과 공개 경계

- API 키는 서버 비밀 환경변수로만 관리합니다.
- 원본 응답, 닉네임, OUID, 실제 matchId와 가명 매핑표는 최소 권한으로 제한합니다.
- 공개 이슈·PR·스크린샷·로그에는 식별 가능한 값을 넣지 않습니다.
- 데이터 유출이 의심되면 접근을 차단하고 범위를 보존해 조사하며, 공식 약관 8.5에 따라 NEXON에 24시간 안에 통지하고 관련 법령의 신고 의무도 확인합니다.
- 공개 통계가 필요하면 식별 위험과 표본 수를 검토하되, 집계했다는 이유만으로 TTL·삭제 의무가 사라진다고 가정하지 않습니다.

## 8. 현재 구현 상태와 배포 게이트

현재 앱의 성공 응답 캐시는 프로세스 메모리에서 15초만 유지되고 영구 DB는 없습니다. 그러나 로컬 `captured` 파일과 향후 추천·연구 로그는 별도 수명주기 관리가 필요합니다.

다음 조건을 모두 충족하기 전에는 실제 사용자 데이터를 장기 저장하는 기능을 운영 배포하지 않습니다.

- `pulled_at`·`expires_at` 저장과 만료 데이터 자동 삭제
- 원본부터 파생값·캐시·백업까지 이어지는 삭제 테스트
- 이용자 요청 및 동의 철회 절차
- 실제 동작과 일치하는 개인정보처리방침
- 공개 저장소의 fixture가 합성 데이터뿐이라는 검토
- 약관 변경일과 이 문서의 재검토 날짜를 기록하는 운영 점검
